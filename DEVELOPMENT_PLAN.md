# DEVELOPMENT_PLAN.md — «Последнее убежище»

Статус: **в разработке**. Phase 0 и Phase 1 (вертикальный срез) реализованы и проверены. Стек подтверждён владельцем проекта: Vanilla DOM (без UI-фреймворка), контент событий — типизированные TS-модули, минимальная инициализация Yandex Games SDK уже в Phase 0 (без рекламы).

Каждая фаза — это вертикальный срез: минимальная реализация → тест вручную → проверка стыковки с уже готовыми системами → расширение. Порядок фаз ниже — рекомендованный; фазы 3–6 частично пересекаются, т.к. вместе образуют MVP-цикл (раздел 33 брифа).

## Phase 1 — Игровой прототип
Цель: скелет экранов и переходов между ними, без реального геймплея.

- [x] Минимальный роутер экранов (Shelter / Expedition / Event / Result / GameOver) — `AppController` + стейт-машина, без библиотек
- [x] Базовый layout под мобильный и десктопный вьюпорт (CSS, крупные touch-friendly кнопки, safe-area)
- [x] Центральный игровой стейт (`GameState`) с одним источником правды
- [x] Простой event bus для связи модулей между собой (`game/EventBus.ts`)
- [x] Реальный (не заглушечный) контент MVP-уровня на каждом экране — 5 персонажей, 3 постройки, 3 события

Критерий готовности: можно вручную пройти по всем экранам и вернуться в начало. **Выполнено и проверено Playwright-смоук-тестом (полный цикл Shelter → Expedition → Event → Result → Shelter).**

## Phase 2 — Основной gameplay loop
Цель: реализован полный цикл дня из раздела 8 брифа на заглушечных данных.

- [x] Функция `advanceDay()`: тратит ресурсы, повреждает убежище при голоде, увеличивает счётчик дня — `game/GameLoop.ts`
- [x] Проверка условий поражения (здоровье убежища ≤ 0 → game over)
- [x] Цикл: Убежище → выбор персонажа → выбор длительности экспедиции → событие → результат → возврат в убежище → следующий день
- [x] Полный игровой цикл работает на реальных (не заглушечных) MVP-данных

Критерий готовности: можно проходить цикл по кругу и довести партию до game over. **Выполнено** (формулы экономики — черновые, уточняются в Phase 7).

## Phase 3 — Убежище
- [ ] Модель построек: склад, генератор, мастерская (данные + эффекты)
- [ ] Экран убежища: отображение ресурсов, персонажей, построек
- [ ] Потребление ресурсов за день (еда/вода персоналом, энергия постройками)
- [ ] Простое улучшение постройки (стоимость → эффект)
- [ ] UI-виджет ресурсов (иконка + число + тренд)

Критерий готовности: постройки реально влияют на баланс ресурсов день за днём.

---

## Phase 4 — Персонажи
- [ ] Модель персонажа: имя, здоровье, характеристики (HEALTH/SKILL/LUCK/MORALE), профессия, настроение, отношение к игроку
- [ ] 5 стартовых персонажей с уникальными профилями (данные, не хардкод в логике)
- [ ] Экран персонажа (карточка с характеристиками)
- [ ] Влияние состояния (ранен/в экспедиции/недоступен) на возможность отправки

Критерий готовности: персонажей можно выбрать, посмотреть их характеристики, они меняются от последствий событий.

---

## Phase 5 — Экспедиции
- [ ] Выбор персонажа + длительности (1/2/3/5 дней)
- [ ] Формула риск/награда от длительности и характеристик персонажа
- [ ] Резервирование персонажа на N дней (недоступен для других действий)
- [ ] Возврат экспедиции: определение исхода (успех/частичный/провал) на основе риска

Критерий готовности: разные длительности дают ощутимо разный риск и награду.

---

## Phase 6 — Система событий
- [ ] Структура данных `Event` (см. раздел 12 брифа: title/description/requirements/choices/outcomes/risks/flags)
- [ ] Загрузчик/реестр событий, не завязанный на игровую логику (данные отдельно от кода)
- [ ] Движок выбора события по условиям (requirements, флаги, состояние персонажа)
- [ ] Экран события: описание + варианты выбора
- [ ] Экран результата: что произошло, награды, последствия
- [ ] Минимум 20 событий с содержательными выборами (раздел 17 брифа — не «+100/-100»)
- [ ] Базовая система флагов для цепочек событий (раздел 13)
- [ ] 1 тестовая цепочка событий на 3-4 звена

Критерий готовности: события выпадают по условиям, выбор ощутимо влияет на исход, минимум одна цепочка работает от начала до конца.
