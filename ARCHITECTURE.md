# ARCHITECTURE.md — «Последнее убежище»

Статус: **предложение на утверждение**. Репозиторий на момент анализа пуст (нет package.json, нет исходников) — стек ниже не привязан к существующему коду, это рекомендация с нуля.

## 1. Стек (рекомендация)

| Слой | Выбор | Почему |
|---|---|---|
| Язык | TypeScript | AI-агентам и людям проще поддерживать типизированный код; ловит ошибки в структурах событий/персонажей на этапе сборки |
| Сборка | Vite | Мгновенный dev-сервер, минимальный конфиг, маленький продакшн-бандл, легко настроить относительные пути под Yandex Games |
| UI-слой | Vanilla DOM + CSS, без фреймворка | Игра — по сути меню/карточки/текст с переходами между экранами, а не real-time рендеринг. React/Vue/Preact добавили бы вес бандла и слой абстракции, не нужный для этого объёма экранов (раздел 26, 31 брифа: не усложнять) |
| Состояние | Простой самописный стор (единый `GameState` объект + подписки/события) | Соответствует правилу «B простое надёжное» из брифа; кол-во экранов (5-6) не оправдывает Redux/MobX/итд |
| Стили | Обычный CSS (возможно CSS-переменные для тем), без CSS-in-JS | Ноль рантайм-издержек, критично для слабых Android |
| Хранение | `localStorage` + собственный сериализатор с версионированием схемы | Простое, надёжное, без сети; API Яндекс Игр подключается позже только если понадобится (раздел 20) |
| Аудио | Нативный `Audio`/`HTMLAudioElement`, без аудио-движка | 8-10 коротких сэмплов не требуют Howler.js и подобных библиотек |
| Реклама | Yandex Games SDK (`ysdk`) | Обязателен для публикации, единственная непереговорная зависимость |

**Альтернатива, которую стоит явно обозначить:** если в ходе Phase 1-2 vanilla DOM-подход начнёт давать много ручной синхронизации UI/state (баги рассинхронизации), можно перейти на Preact (~3KB) с `htm` вместо JSX — без сборочных изменений на уровне Vite. Это архитектурное решение среднего уровня риска, поэтому оно вынесено в открытые вопросы ниже, а не выбрано односторонне.

Ничего из перечисленного не устанавливается, пока план не подтверждён (Phase 0 — первая фаза после подтверждения).

## 2. Структура проекта

```
src/
  game/            # Ядро игровой логики, не знает про DOM
    GameState.ts       # Единый объект состояния + типы
    GameLoop.ts         # advanceDay(), переходы дня
    EventBus.ts          # Простая шина событий модуль-модуль
  player/            # Ресурсы, валюта, счётчик дня, состояние здоровья убежища
  shelter/           # Постройки, их эффекты, апгрейды
  characters/         # Модель персонажа, реестр стартовых персонажей, характеристики
  expeditions/         # Логика выбора длительности, формулы риск/награда, резолвинг исхода
  events/            # Структуры данных событий (данные отдельно от движка), движок выбора события, цепочки/флаги
    data/              # *.ts или *.json с контентом событий — НЕ логика
    EventEngine.ts
  economy/            # Балансовые формулы, конфиг чисел (см. GAME_BALANCE.md)
  ui/                # Экраны и компоненты, только рендер + обработка ввода
    screens/
      ShelterScreen.ts
      ExpeditionScreen.ts
      EventScreen.ts
      ResultScreen.ts
      GameOverScreen.ts
    components/
  save/              # Сериализация/десериализация, версии схемы, миграции
  ads/               # Обёртка над Yandex Games SDK, rewarded-точки входа
  utils/             # Чистые хелперы без побочных эффектов
main.ts             # Точка входа, инициализация
```

**Принцип границ**: `game/`, `player/`, `shelter/`, `characters/`, `expeditions/`, `events/`, `economy/` не импортируют ничего из `ui/`. UI только читает состояние и вызывает функции игровой логики. Это даёт возможность тестировать всю игровую логику без DOM и без браузера.

## 3. Поток данных

```
UI-действие игрока
   → вызов функции в game/*  (напр. sendExpedition(characterId, duration))
   → изменение GameState
   → EventBus.emit('stateChanged', ...)
   → UI-слой перерисовывает затронутые экраны
   → save/ автосохраняет при контрольных точках (конец дня, важное действие)
```

Нет двусторонней магии: UI не мутирует состояние напрямую, только через функции модулей `game/*`.

## 4. Система событий (техническая часть раздела 12 брифа)

- Событие — объект данных (`EventDefinition`), контент живёт в `events/data/`, отдельно от `EventEngine.ts`.
- `EventEngine` на входе получает текущий `GameState` + флаги, возвращает список подходящих событий (`requirements` проверяются как чистые предикаты).
- `choices[].outcomes` — тоже данные: изменения ресурсов, характеристик, флагов, отношений. Движок применяет их единообразно, без `if` на конкретное событие в коде движка.
- Цепочки — через `flags`: событие A ставит флаг `signal_heard_day12`, событие B требует этот флаг + минимальное количество прошедших дней.
- Добавление нового события = новый файл данных, без изменений `EventEngine.ts` (это и есть требование брифа «без переписывания основной логики»).

## 5. Сохранения

- `GameState` сериализуется в JSON, пишется в `localStorage` под ключом с префиксом схемы, напр. `save_v1`.
- При загрузке: попытка парсинга → валидация обязательных полей → при ошибке — не крашим игру, предлагаем новую игру и логируем причину.
- Версионирование: поле `schemaVersion` в сейве; миграции — чистые функции `migrateV1toV2(data)` в `save/migrations.ts`, применяются последовательно.

## 6. Производительность

- Без canvas/WebGL на MVP — чистый DOM с ограниченным числом одновременно видимых узлов (один экран за раз).
- Ленивая загрузка контента событий не требуется на объёме 20-30 событий (JSON достаточно мал), пересмотреть при росте контента на порядок.
- Изображения — оптимизированные, с явными размерами, без каких-либо тяжёлых ассетов на старте.

## 7. Тестирование

- Игровая логика (`game/`, `expeditions/`, `events/`, `economy/`) — юнит-тесты на чистые функции (Vitest, идёт в комплекте с Vite-экосистемой, минимальная зависимость).
- UI — ручное тестирование на каждом вертикальном срезе (автоматизация UI — не приоритет для маленькой команды на этом этапе).

## 8. Зависимости (минимальный старт)

Только: `vite`, `typescript`, `vitest` (dev), Yandex Games SDK (подключается в Phase 10, не раньше). Никаких UI-фреймворков, state-менеджеров, аудио- или анимационных библиотек на старте — добавляются только при доказанной необходимости (раздел 4, 31 брифа).

## 9. Открытые архитектурные решения (нужно подтверждение владельца)

1. **Vanilla DOM vs Preact** — см. раздел 1. Рекомендация: начать с vanilla, пересмотреть при первых признаках боли на Phase 1-2.
2. **Формат данных событий**: TypeScript-модули (типобезопасно, но требует сборки для правок) vs JSON (проще редактировать, в т.ч. не-программисту, но без типов из коробки без доп. валидации). Рекомендация: TS-модули с общим интерфейсом `EventDefinition` — команда маленькая и техническая, типобезопасность важнее.
3. **Объём Yandex SDK на старте**: подключать ли SDK уже в Phase 0 (для ранней проверки деплоя) или откладывать до Phase 10 по плану. Рекомендация: минимальная инициализация SDK в Phase 0 (без рекламы) — снижает риск сюрпризов при финальной публикации.
